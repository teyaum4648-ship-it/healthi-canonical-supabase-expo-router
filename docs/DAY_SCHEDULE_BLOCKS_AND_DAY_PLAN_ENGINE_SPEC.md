# Healthi Day Schedule Blocks + Day Plan Engine Spec

## 1. Purpose

The Day Schedule Blocks layer lets a user mark the shape of their day inside Healthi: work, class, commute, exercise, meal, free time, recovery, social, appointment, and sleep.

The Day Plan Engine uses those blocks as real-world constraints. It should later combine schedule context with Sleep + Rhythm energy windows, readiness, nutrition and food response signals, training or movement capacity, wind-down timing, and user preferences.

The product goal is not to become a full calendar app. The goal is to help Healthi answer:

- What parts of the day are already constrained?
- Where are useful openings?
- When is deep work most likely to fit?
- When is movement or training best timed?
- Where should meals or snacks be placed?
- When should recovery, reset, caffeine cutoff, and wind-down happen?
- What is estimated versus directly entered by the user?
- How confident is Healthi in the plan?

## 2. Product Boundary

Day Schedule Blocks are user-entered or Healthi-generated time blocks inside the app.

In scope for V1:

- Manual in-app blocks.
- A simple day view.
- Block categories and labels.
- Start time, end time, optional recurrence hint, and optional flexibility.
- Local/demo support.
- Deterministic plan output.
- Clear source and confidence.
- General wellness timing suggestions.

Out of scope for V1:

- Calendar sync.
- Native calendar permissions.
- Google Calendar.
- Apple Calendar.
- Calendar invites.
- Contact or attendee access.
- Background calendar polling.
- AI scheduling.
- Automatic rescheduling without explicit user action.
- Push notification scheduling.
- Full task management.

Healthi should speak in planning language:

- "suggested window"
- "based on available data"
- "estimated"
- "likely"
- "fits your current day"
- "confidence"
- "adjust if this does not match your day"

Healthi should not imply certainty or authority over the user's schedule.

## 3. In-App Schedule Blocks Model

Schedule blocks are the user's stated day constraints and intentions. They should be simple enough to enter quickly, but structured enough for a planner to reason over.

### Block Categories

Recommended V1 categories:

- `work`: work shift, office hours, focused job responsibilities.
- `class`: school, lecture, study lab.
- `commute`: driving, public transit, walking commute.
- `exercise`: training, sport, planned workout.
- `meal`: breakfast, lunch, dinner, snack, planned fueling.
- `free_time`: open personal time.
- `recovery`: nap, breathing, quiet reset, mobility, low-stimulation time.
- `social`: plans with friends, partner, family, community.
- `appointment`: appointment, meeting, errand with fixed time.
- `sleep`: target sleep window or logged sleep block.
- `other`: fallback category.

### Block Intent

Each block should include whether it is:

- `fixed`: user is unlikely to move it.
- `flexible`: user can shift it inside a range.
- `preferred`: user prefers it, but it is not required.
- `suggested`: generated by Healthi.

The planner should protect fixed blocks, gently use flexible blocks, and clearly label suggested blocks.

### Conflict Rules

If blocks overlap:

- User-entered fixed blocks win over suggested blocks.
- User-entered blocks win over Healthi-generated blocks.
- Sleep and wind-down should be protected unless the user marks the block as flexible.
- The engine should return conflicts instead of silently deleting blocks.
- Missing or unclear data lowers confidence.

### Minimal User Flow

V1 should let the user:

- Add a block.
- Pick category.
- Set start and end time.
- Mark fixed or flexible.
- Add an optional label.
- Delete or edit the block.
- See Healthi suggested blocks separately from user-entered blocks.

## 4. External Calendar Sync Boundary, Future Only

External calendar sync is a future layer. The current design should leave room for it, but should not implement it.

Future sync sources may include:

- Google Calendar.
- Apple Calendar.
- Outlook.
- Device calendar APIs.

Future synced events should map into the same internal `ScheduleBlock` model with:

- `source_type: 'external_calendar'`
- `external_source`
- `external_event_id`
- `source_confidence`
- `synced_at`
- read-only default behavior unless user imports or converts the event.

Future privacy boundary:

- Ask for explicit permission.
- Explain what is imported.
- Allow disconnect.
- Avoid storing unnecessary event details.
- Prefer category and time range when full event text is not needed.

V1 should not request permissions or import external events.

## 5. Day Plan Engine Architecture

Keep the stack separated:

```text
Schedule Blocks = user constraints and stated day shape
Sleep + Rhythm = estimated energy and timing windows
Readiness = capacity and intensity context
Nutrition/Food Response = fueling timing and response context
Movement/Training = movement capacity and training suggestions
Day Plan Engine = fits recommendations into the user's actual day
Dashboard = displays the most useful plan summary
```

The Day Plan Engine should be a pure deterministic layer that accepts inputs and returns suggested windows, conflicts, confidence, and reason codes.

The engine should not:

- Decide medical safety.
- Generate a workout program.
- Generate a full meal plan.
- Sync calendars.
- Use AI.
- Override user constraints.

The engine should:

- Find open windows.
- Score windows against rhythm and readiness context.
- Fit suggested actions into available time.
- Return alternatives when the best window is blocked.
- Include source and confidence.
- Explain with reason codes.

## 7. How Rhythm Windows Influence Recommendations

Sleep + Rhythm should provide timing windows, not commands.

The Day Plan Engine should use rhythm outputs to score open windows:

- Deep work prefers high-energy or rising windows.
- Harder exercise prefers stronger energy windows when readiness allows.
- Walks and light movement can fit lower-pressure windows or post-meal windows.
- Breathing/reset can fit energy dips, transition points, or after dense schedule blocks.
- Nap suggestions should only appear when rhythm and sleep debt support a short rest and a window exists.
- Caffeine cutoff should be placed before the wind-down sequence.
- Wind-down start and target bedtime should remain visible even when the day is crowded.

If a rhythm-recommended window is blocked, the engine should return the next best available window with a reason code like `exercise_window_blocked`.

Example:

```text
Deep work best rhythm window: 9:00 AM - 11:30 AM
Schedule has class from 9:30 AM - 10:45 AM
Suggested deep work: 11:00 AM - 12:00 PM
Reason codes: rhythm_peak_matched, user_fixed_block_protected
Confidence: medium
```

## 8. How Food Recommendations Fit Into Schedule

Food recommendations should be timing and support suggestions, not rigid meal plans.

The Day Plan Engine should consider:

- Meal blocks already entered by the user.
- Long gaps without food.
- Training or movement blocks that may need nearby fueling.
- Food response signals from logged meals.
- User's Food Pattern Profile, when available.
- Rhythm dips that may overlap with long food gaps.

V1 suggestions may include:

- "Add a meal window before your afternoon block."
- "A simple snack may fit before training."
- "Keep dinner earlier if wind-down is close."
- "Log how you feel after this meal to improve the estimate."

The engine should not:

- Create detailed meal plans.
- Assign calories without targets.
- Shame food choices.
- Use rigid diet language.
- Label foods as good or bad.

Food timing should respect fixed blocks and user preferences.

## 9. How Exercise Timing Fits Into Schedule

Exercise timing should be based on schedule fit, rhythm windows, and readiness context.

The Day Plan Engine should use movement/training input to decide:

- Whether a workout block already exists.
- Whether there is an open window long enough.
- Whether a lighter movement window is more appropriate.
- Whether commute, meal, or wind-down timing makes the window less useful.

The engine may suggest:

- Training window.
- Walk or light movement window.
- Recovery/mobility window.

The engine should not generate the workout itself. It should only suggest timing and context.

Example:

```text
Suggested exercise: 12:15 PM - 1:00 PM
Why: open window, rhythm still supportive, enough space before next meal block
Confidence: medium
```

If readiness is limited, the engine should change intensity language:

- Prefer "walk"
- "light movement"
- "recovery window"
- "keep it easy"

It should avoid certainty or pressure.

## 10. How Sleep/Wind-Down Timing Fits Into Schedule

Sleep and wind-down should be first-class schedule constraints.

The engine should use:

- Target bedtime from Sleep + Rhythm.
- Wind-down start.
- Caffeine cutoff.
- Existing sleep block.
- Late work, class, social, or appointment blocks.
- User flexibility.

The output should make visible:

- Target bedtime.
- Wind-down start.
- Caffeine cutoff.
- Any conflict between late blocks and wind-down.

If a late block conflicts with wind-down:

- Do not scold.
- Do not force rescheduling.
- Suggest a smaller reset or shortened wind-down if appropriate.
- Lower confidence when the evening is constrained.

Example:

```text
Wind-down target: 9:30 PM
Late appointment: 9:00 PM - 10:00 PM
Suggestion: use a 10-minute reset after the appointment and keep target bedtime visible
Confidence: low
```

## 11. Persistence Recommendations

V1 persistence should be simple:

### Persist Now

- `schedule_blocks`
- `day_plan_preferences`

Recommended `schedule_blocks` fields:

- `id`
- `user_id`
- `date`
- `category`
- `label`
- `start_at`
- `end_at`
- `timezone`
- `flexibility`
- `source_type`
- `source_confidence`
- `is_user_confirmed`
- `recurrence_hint`
- `notes`
- `external_source`
- `external_event_id`
- `reason_codes`
- `created_at`
- `updated_at`

Recommended `day_plan_preferences` fields:

- `user_id`
- `preferred_deep_work_duration_minutes`
- `preferred_exercise_duration_minutes`
- `preferred_walk_duration_minutes`
- `meal_gap_watch_minutes`
- `wind_down_buffer_minutes`
- `default_commute_buffer_minutes`
- `created_at`
- `updated_at`

### Recompute

- Daily plan suggestions.
- Conflict list.
- Window scoring.
- Dashboard summary.

### Delay

- Cached daily plans.
- External calendar sync tables.
- Notification scheduling.
- AI-generated plans.
- Historical adherence analytics.

The engine should be able to recompute from persisted blocks and current Healthi signals.

## 12. Dashboard Integration

Dashboard should show only the highest-signal parts of the plan.

Recommended dashboard surfaces:

- Today's main window: deep work, movement, or recovery.
- Next suggested block.
- Wind-down start.
- Caffeine cutoff when relevant.
- One schedule conflict or constraint if important.
- Confidence/source label.

Example dashboard copy:

```text
Today's plan
Deep work fits best before 11:30 AM.
Next: walk window around 3:20 PM.
Confidence: medium. Based on your schedule and rhythm estimate.
```

The dashboard should not show every schedule block. The full schedule view can live in a dedicated Plan or Day view later.

## 13. V1/V2/V3 Rollout

### V1: In-App Blocks + Deterministic Suggestions

- Manual schedule blocks.
- Demo/local support.
- Pure Day Plan Engine.
- Open-window detection.
- Rhythm-aware timing suggestions.
- Basic meal, movement, recovery, caffeine cutoff, and wind-down suggestions.
- Dashboard summary.
- No external calendar sync.

### V2: Smarter Personalization

- Repeating block support.
- User correction flow.
- Preference learning.
- Better conflict handling.
- Planning history.
- Stronger dashboard integration.
- Suggested block acceptance/dismissal.
- Optional reminders, if product decides to add them later.

### V3: External Calendar + Adaptive Planning

- Google Calendar sync, if approved.
- Apple Calendar sync, if approved.
- Device calendar sync, if approved.
- Permissioned read-only imports.
- Source reliability scoring.
- Adaptive window scoring from user behavior.
- Calendar conflict explanations.
- Optional plan export.

V3 should still preserve the same internal `ScheduleBlock` and `DayPlanOutput` concepts.

Use:

- estimated
- likely
- suggested
- based on available data
- confidence
- general wellness guidance
- may fit better
- current rhythm estimate
- your schedule suggests

Do not use:

- diagnosis
- diagnose
- treatment
- cure
- prescribe
- prescription
- adrenal
- HPA
- cortisol
- hormone
- clinical
- medical decision
- dysregulated
- dysfunction
- detox
- toxin
- toxic
- cleanse
- cheat meal
- guilt-free
- bad food
- metabolic type
- metabolic typing

## 15. Open Questions

- Should schedule blocks live under a dedicated Plan tab or inside Dashboard first?
- Should V1 support recurring blocks, or only same-day blocks?
- Should the user be able to create templates like "workday", "school day", or "travel day"?
- How much detail should Healthi ask for when the user marks a work/class block?
- Should flexible blocks include an allowed time range?
- Should meal suggestions appear as blocks or as lightweight prompts?
- Should wind-down be a block, a dashboard signal, or both?
- How should the app distinguish a user-planned exercise block from Healthi's suggested exercise timing?
- Should local/demo schedule blocks use the same AsyncStorage pattern as local demo nutrition?
- Should accepted Healthi suggestions become user-confirmed schedule blocks?
- What is the minimum useful dashboard summary for users who do not want to maintain a schedule?
- How should conflicting blocks be displayed without making the app feel stressful?
